Spec Kit: pros and cons.

# pros
  • Backed by GitHub, the largest community
  • Agent-agnostic: Copilot, Claude, Gemini, Codex…
  • Constitution: rules every feature inherits
  • Strong at greenfield, rich templates
  • Extensible: presets and extensions
# cons
  • Verbose: thousands of markdown lines to review
  • Heavy for a bug fix or a small change
  • Specs are per change: spec-first, they drift
  • About 2× the tokens of OpenSpec (slide 15)

OpenSpec: deltas.

/opsx:propose  → change
/opsx:apply    → code
/opsx:archive  → merge
               into specs/
# spec-anchored
Archived deltas keep specs/ current.
~/app $ ./review openspec --honest

OpenSpec: pros and cons.

# pros
  • Brownfield first: describe a change, not a system
  • Short documents, easy to review
  • Living specs, unlike Spec Kit and Kiro
  • No API key, no MCP, a plain npm CLI
  • Lowest token use in public benchmarks
# cons
  • No agents, no roles: you are the PM and architect
  • Thin on greenfield discovery and research
  • Young and fast-moving: 1.0 → 1.14 in 2026
  • v1.0 broke the old /openspec:* commands

BMAD: pros and cons.

# pros
  • Covers the whole lifecycle, not only coding
  • Strong discovery: brief, PRD, PRFAQ, research
  • Adversarial review catches design flaws
  • Quick flow for small work
  • Modules: testing, game dev, custom agents
# cons
  • Steep learning curve, lots of vocabulary
  • Slow: hours to days of planning per feature
  • Largest footprint: 235 files installed
  • Most tokens of the three
  • Name is trademarked (code stays MIT)

~ $ cat CRITICISM.md

What they all share.

# waterfall in markdown?
Big upfront design, again. Fine when the problem is known, painful when it is not.
# review overload
Verbose, repetitive documents. Reviewing them can cost more than reviewing code.
# still non-deterministic
A perfect spec does not stop the agent from ignoring it. Tests still decide.
# one size fits none
A typo fix through a full pipeline is a sledgehammer for a nut.

Which one?

existing codebase, frequent changes?
  └─▶ OpenSpec
new product, many agents, one standard?
  └─▶ Spec Kit
fuzzy idea, needs PM + architecture work?
  └─▶ BMAD (quick flow for the small stuff)
long autonomous runs, Claude Code?
  └─▶ GSD
small fix?
  └─▶ plan mode. No framework.
# rule of thumb
Pay for ceremony only where a mistake costs more than the tokens.
